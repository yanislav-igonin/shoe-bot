# Text Provider Settings Design

## Goal

Address GitHub issue #34 by allowing the bot's user-facing text generation to
switch between xAI, Together AI, and OpenRouter without a restart. Keep xAI as
the default and do not add OpenAI as a text provider.

## Settings and configuration

Store two global rows in the existing `settings` table:

| key | initial value |
| --- | --- |
| `textProvider` | `xai` |
| `textModel` | `grok-4` |

Supported provider values are exactly `xai`, `togetherai`, and `openrouter`.
`textModel` is an opaque provider model ID. Each user-facing text generation
loads both settings from PostgreSQL so manual updates take effect immediately.
Missing, empty, or unsupported settings fail explicitly; there is no provider
fallback.

Add optional `OPENROUTER_API_KEY` and keep the existing optional
`TOGETHER_API_KEY`. A provider key is validated only when that provider is
selected, so xAI operation does not require either key. Secrets stay in the
environment and are never stored in settings or committed.

## Provider routing

Keep routing local to `src/lib/prompt.ts`, matching the direct image-provider
pattern. The selected settings produce an AI SDK language model:

- xAI uses the existing native `xai(model)` provider;
- Together AI uses the OpenAI-compatible adapter at
  `https://api.together.ai/v1`;
- OpenRouter uses the same adapter at `https://openrouter.ai/api/v1`.

The existing prompt/context construction, multimodal inputs, response trimming,
no-answer fallback, and Telegram chunking remain shared. Provider-specific
classes, registries, and fallback chains are out of scope.

The selected provider applies to normal conversation responses and the text
description generated by `/shicture`. Intent classification remains on the
fixed `grok-3-mini` xAI model because it is an internal routing operation, not a
user-facing completion.

## Database migration

Add one MikroORM migration that inserts `textProvider=xai` and
`textModel=grok-4` with `ON CONFLICT ("key") DO NOTHING`. Existing installations
gain defaults without overwriting operator choices; fresh installations reach
the same final seed state after all migrations.

## Errors and testing

Configuration and provider errors propagate into existing controller logging
and generic user-facing error handling. Tests cover settings parsing, missing
provider keys, provider-to-model routing, and migration seed state. No live API
test is required because it would spend provider credit and make CI depend on
external services.

Validation commands:

```text
npm test
npm run lint
npm run typecheck
npm run build
```
